Lab / 01 · Rate limiting

How do you stop one user from taking down your API?

A rate limiter decides, in under a millisecond, whether a request gets through. Here’s a token bucket running live. Give each user a bucket of tokens; every request spends one; tokens refill at a steady rate. Empty bucket means 429.

The architecture

The check happens before your request ever reaches business logic, and the counter lives in Redis so every server instance shares one view of each user.

The core of it

-- token_bucket.lua (runs atomically inside Redis) local tokens = tonumber(redis.call('HGET', KEYS[1], 'tokens') or ARGV[1]) local last = tonumber(redis.call('HGET', KEYS[1], 'ts') or ARGV[3]) local refill = math.floor((ARGV[3] - last) / ARGV[2]) tokens = math.min(ARGV[1], tokens + refill) if tokens < 1 then return {0, tokens} end redis.call('HSET', KEYS[1], 'tokens', tokens - 1, 'ts', ARGV[3]) return {1, tokens - 1}

Trade-offs I weighed

Token bucket

Allows short bursts, smooth over time. Good default for user-facing APIs.

Sliding window

Stricter and fairer at window edges, but costs more memory per user.

Why Lua in Redis

Read-check-write in one atomic step, so two servers can’t both spend the last token.
